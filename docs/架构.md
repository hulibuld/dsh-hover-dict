# dsh-hover-dict 架构

DSH 插件。鼠标停在助手回复或思考内容里的英文单词上，弹出词性、中文释义与考纲标签；
点一下就地展开完整词条。离线词库，不联网、不要 API key、**不改正文 DOM**。

这份文档是给实现者的施工图。函数签名、数据契约、时序参数都在这里定死，
照着填空即可。凡是「必须 / 不许」的地方，都是踩过坑或者宿主契约的硬约束，别自行放宽。

---

## 0. 一句话架构

宿主侧是一台**静态文件服务器**（吐三个词库文件）；浏览器侧持有**全部查询能力**
（一次加载进内存建索引，之后零网络）。所有交互逻辑在浏览器侧，宿主侧不参与查词。

## 2. 两条硬约束怎么落地的

### 约束一：不改正文 DOM

**绝不允许**把单词包成 `<span>`。一旦包了：

1. 宿主的 markdown 渲染器每次重渲染都会把我们插的节点丢掉（流式输出时每秒重渲染），
   我们的监听全部指向已脱离文档的旧节点；
2. React 的 diff 会因为我们插了节点而错位，最坏的情况是用户消息里出现乱码；
3. 原文可复制性被破坏 —— 用户复制一段话会带上我们的 `span`。

替代做法分两步，两个方向都不用写 DOM：

**反查**（`hit.js` 的 `caretAt`）：

```
pointermove(x, y)
  → document.caretRangeFromPoint(x, y)      Chromium / WebKit
  → document.caretPositionFromPoint(x, y)   Firefox（退化）
  → { node: Text, offset: number }
```

这两个 API 是浏览器自己提供的「这个坐标落在哪个字符上」，不依赖我们预先标记任何东西。

**量矩形**（`anchor.js` 的 `anchorOf`）：

```
new Range() → setStart(node, start) → setEnd(node, end)
  → range.getClientRects()
```

`getClientRects()` 给出这个词在视口里的所有矩形片段。跨行时会有多个，
**必须逐段画**——只画外接矩形会把整行点亮。

**画**（`overlay.js`）：

高亮与浮层都渲染进 `shell.overlay` slot，是 frame-wide 的浮动层，用
`position: fixed` 定位在视口坐标上。这一层与正文是兄弟关系，不嵌套，
所以宿主重渲染正文时不会影响我们，我们也不影响它。

### 约束二：数据全打包

`data/` 下三个文件随包分发，运行时**不联网**（除了向宿主自己的 prefix 路由取这几个文件）。
体积与放置决策见下一节。

## 3. 决策：词库放宿主侧还是全塞客户端

**结论：全塞客户端。一次加载进内存建索引，之后零网络。**

这是本架构最重要的一个决策，所以把算法和数据都摆出来。

### 3.1 两个候选方案

| | A. 宿主侧查询 | B. 全塞客户端（选定） |
|---|---|---|
| 运行时 | 每次悬停发一次 HTTP | 首次加载后零请求 |
| 单次延迟 | 本机 IPC 约 1–3 ms，但**不可预测**（宿主忙时排队） | Map/对象直查，实测 **0.05–0.07 µs** |
| 命中率依赖 | 网络可靠性 | 内存 |
| 失败模式 | 宿主管道堵塞 → 浮层迟迟不弹 | 首次加载慢 15 ms |
| 首屏成本 | 0 | 约 15 ms（一次性，首帧后触发） |
| 数据重跑 | 立刻生效 | 下次刷新页面生效（可接受：改词库本来就该刷新） |

### 3.2 为什么 A 不行

悬停是**高频、且对延迟极度敏感**的交互。用户在读一段英文回答，鼠标顺着句子划过去，
一秒内可能掠过 10 个词。这个动作的心理预期是「手指停下的那一刻词义就在」，
超过 100 ms 就会觉得卡。本机 IPC 的 1–3 ms 看起来够快，但它有三处不可控：

1. 宿主在流式输出时主线程是忙的，请求会排在 markdown 渲染之后；
2. 每个词一次请求，一串划过能堆出十几个待处理请求，反而把宿主拖慢；
3. 请求失败（宿主正在重载、路由还没注册好）时，浮层只能显示错误或者不显示，
   而用户根本不知道该怪什么。

而 B 的查询成本是 0.05 µs —— 比一次函数调用重不了多少，完全在主线程的预算里。

### 3.3 那 3 MB 的解析成本呢（实测，用真数据）

初稿是按任务书给的「1.6 MB / 4.3 万键」估的。数据组实际产出是 **3.0 MB**
（`dict.dat` 2.07 MB + 变位索引（运行时从词条 forms 现场建，不再单独存文件） 0.93 MB），所以这里的数**全部用真实文件重测过**，
初稿的合成数据估算作废。

数据组实测产出（20,499 词条、46,011 查询键）：

| 操作 | 中位数 | p90 |
|---|---|---|
| `JSON.parse(dict.dat)`（2.07 MB） | 16.4 ms | 17.1 ms |
| `JSON.parse(变位索引)`（0.93 MB） | 13.6 ms | 14.9 ms |
| 两次 parse 合计 | **29.5 ms** | 31.1 ms |
| 新方案：parse dict + 遍历建 Map（§4.4） | 31.1 ms | 32.3 ms |
| 单次查询（Map.get） | 0.07 µs | — |

**结论：一次性 29–32 ms，之后每查一次 0.07 µs。**

这个数比初稿估的 15 ms **翻了一倍**，位置也变了：一帧 16.7 ms，29 ms 是**两帧**。
但结论不变，理由三条：

1. 它是一次性成本，不在悬停路径上。悬停路径永远是 0.07 µs 的内存直查。
2. 触发时机是首帧之后的 `requestIdleCallback`，此时界面已渲染完、用户正在读第一段
   回答，掉两帧无感。
3. 相比"每次悬停发一次 HTTP"（§3.2），29 ms 的一次性代价换永久零延迟，仍然是赚的。

外推：低端笔记本约 4×（120 ms），老安卓 webview 约 8×（240 ms）。在最差的设备上
这已经能被察觉（约 14 帧），但它发生在加载期而不是交互期，用户感知到的是
"词库加载中"多了一瞬，不是"悬停卡顿"。

**这次重测推翻了一件事**：初稿说"1.6 MB 解析 12–16 ms，可以接受"，当时是按
合成数据的乐观估计。真数据是 3 MB，如果词库再涨（比如补回英英释义与更多例句），
这条线会变得难看。见 §3.4 的例外条款——**现在应当提前准备，而不是等到 5 MB 再改**。

### 3.4 我评估过但没采用的紧凑格式

既然 2–3 MB 的 JSON 解析要 29–32 ms，自然要问：换个格式能不能更快？

下面这组是用**合成数据**测的（4.3 万键的映射表），只为回答「编码方式本身差多少」，
所以绝对值不必对上真数据；结论是看**相对差异**：

| 编码 | 体积 | 解析成本 | 结论 |
|---|---|---|---|
| JSON 对象 | 0.64 MB | 12.8 ms | 基准 |
| JSON 数组对 `[[k,v],…]` | 0.70 MB | 8.4 ms | 略快 |
| TSV 行 `k\tv\n` | 0.58 MB | 8.0 ms | 最快，但要多写一个解析器 |
| 二进制池 + 偏移表 + Int32 下标 | 0.63 MB | 10.7 ms（含 TextDecoder 解码） | 省不下多少 |

再单独试了「字符串池 + 偏移表」解出 2 万词头：**1.9 ms**，比 JSON.parse 的
16 ms（真数据）快 8 倍。这是二进制方案真正的诱惑所在，也是 §3.4 例外条款的备选。

**但最终没有采用，理由有三条：**

1. **体积没省多少。** 二进制池 0.63 MB vs JSON 0.64 MB，几乎一样；gzip 后都是
   0.21 MB。省体积这个动机不成立。
2. **省下的是 10 ms，代价是失去可读性。** 数据组改了字段、或者有人想直接看一眼
   `dict.dat` 里有什么，JSON 打开就能读，二进制得写工具。这个仓库的数据来自第三方
   词库、会随上游更新，可维护性比 10 ms 值钱。
3. **那 10 ms 本来就不在关键路径上。** 它是首帧后的一次空闲回调。真正要优化的
   是「悬停时能不能立刻出词」，而那一层已经是 0.05 µs，换格式对它毫无影响。

**留给实现者的例外条款（已在 2026-10-30 触发一次）**：原定阈值是「`dict.dat` 超过
3 MB 就重开这个决策」。数据组实际产出 `dict.dat` **2.07 MB**，加上必删的
变位索引（运行时从词条 forms 现场建，不再单独存文件） 后的总量从 3.0 MB 降到 2.07 MB（§4.3 删掉恒等冗余、§4.4 改运行时建索引），
所以**暂时守住了阈值，本次不改格式**。

但余量已经很小。一旦后续补回英英释义或更多例句把 `dict.dat` 推过 3 MB，
按原条款处理：改用「二进制池 + 偏移表」，实测解 2 万词头只要 1.9 ms。
届时只换 `dict.js` 的 `loadDictionary` 内部实现，`lookup` 的签名与
`LookupResult` 契约不变，上层一行不用改。**接口必须按这个预期设计**，
不要把「词库是个 JSON 对象」这件事泄漏到 `lookup` 之外。

### 3.5 为什么不做分片按需加载

考虑过「按首字母分 26 个文件，悬停到哪个才取哪个」。否决理由：

- 悬停时**必须先知道有没有这个词**才能决定弹不弹。按需加载意味着每次悬停都要
  等一次网络才能给出判定 —— 这正是 A 方案被否决的原因，绕了一圈又回来了；
- 用户读的英文不按字母顺序分布，读三句话就会把 26 片全取一遍，
  结果还是全量加载，只是多了 26 次请求。

### 3.6 gzip 与缓存

宿主侧的 `index.js` 对三个文件都开 gzip（`accept-encoding: gzip` 且文件 > 1 KiB）。
0.63 MB 压到 0.21 MB，本机 IPC 上差别不大，但它是白送的。

缓存头用 `private, max-age=0, must-revalidate` + ETag，**不用 immutable**：
用户会自己重跑数据脚本，缓存必须能失效。文件系统的 mtime 变了就重算 ETag。

## 4. 数据格式契约

**两个文件**：`data/dict.dat` 与 `data/meta.json`。**这是权威定义**，实现者按它写代码，
数据组按它产数据。

> 本节经 lead 与数据组实测数据复核后重写（原稿设想的是「三个文件 + 数组式 dict」，
> 数据组实际产出是「两个文件 + 以词头为键的对象」，且字段细节有多处出入）。
> 形状以本节为准；论证性说明（为什么列式、为什么不存大小写变体）保留。

### 4.1 `meta.json`

```json
{
  "builtAt": "2026-10-30T08:11:40.883Z",
  "entries": 20499,
  "forms": 46011,
  "withExamples": 2457,
  "source": { "dict": "ECDICT (MIT)", "examples": "Tatoeba (CC BY 2.0 FR)" },
  "bytes": { "dict": 2169363, "forms": 976323 },
  "corpus": { "pairs": 77584, "zhCap": 2, "enCap": 0, "exMax": 1 }
}
```

| 字段 | 类型 | 取值范围 | 说明 |
|---|---|---|---|
| `builtAt` | `string` | ISO 8601 | 构建时刻，只用于诊断展示 |
| `entries` | `number` | 1 – 200000 | 词条数。**必须等于 `Object.keys(dict.dat).length`**，客户端用它做一致性校验 |
| `forms` | `number` | 1 – 500000 | 数据组产出的查询键数。**仅供展示与诊断**，客户端不从它做校验（运行时建索引，键数以实际建出的为准） |
| `withExamples` | `number` | 0 – `entries` | 有例句的词条数 |
| `source` | `Record<string,string>` | — | 来源标识。**界面要展示**，这是合规要求 |
| `bytes` | `Record<string,number>` | — | 构建期产出的体积，只用于诊断 |
| `corpus` | `object` | — | 压缩档位记录：`pairs` 可用句对数、`zhCap` 每组中文义项上限、`enCap` 英英释义上限、`exMax` 每词例句上限 |

**没有 `schema` 字段**（原稿设想过，数据组没产出，也不需要）：版本兼容靠
`entries` 与实际键数的一致性校验兜住；真要做格式版本控制时再加，届时补一个
`schema` 并让客户端在缺失时按 1 处理。

**`corpus` 是给实现者看的产品约束**，不是装饰。当前档位是
`zhCap: 2, enCap: 0, exMax: 1` —— 意思是：

- 每组词性最多 **2 条**中文义项（不是「全部义项」）；
- **完全没有英英释义**（`enCap: 0`，全库 0 条）；
- 每个词最多 **1 条**例句，且只有 2457/20499 ≈ 12% 的词条有。

这直接影响卡片的渲染契约，见 §4.5。

### 4.2 `dict.dat`

一个**以词头为键的对象**，不是数组：

```json
{
  "a":       [[["art.",["累加器","加法器"]],["",["第一个字母 A","一个"]]], "zk gk", 5, [["When I grow up...","我長大後..."]]],
  "abandon": [[["v.",["放弃","抛弃"]],["n.",["放任","无拘束"]]], "gk cet4 cet6 ky toefl gre", 2182, "abandoned,abandoning,abandons", [["Next to China...","在中国的旁边..."]]],
  "arid":    [[["adj.",["干燥的","不毛的"]]], "toefl gre", 10724],
  "a-road":  [[["",["<英>A级公路","主车道"]]], null, null]
}
```

**以词头为键而不是存 `w` 字段**：省掉 20,499 次重复存词头（约 200 KB）。
查"这个词存不存在"变成 `in` 判断，比数组里线性找快得多。

值是一个**变长数组**，槽位含义固定：

| 下标 | 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| 0 | `senses` | `SenseGroup[]` | ✅ | 词性组，长度 ≥ 1。**按中文义项数从多到少排**，最重要的词性在前 |
| 1 | `tags` | `string \| null` | ✅ | 空格分隔的标签串，如 `"cet4 cet6 ky"`；没有就 `null` |
| 2 | `frq` | `number \| null` | ✅ | ECDICT 词频序号，越小越常见；0 记 `null` |
| 3 | `forms` | `string` | ❌ **可省略** | 逗号分隔的变位串，如 `"abandoned,abandoning,abandons"` |
| 4 | `examples` | `Example[]` | ❌ **可省略** | 例句数组，每项 `[英文, 中文]` |

**「可省略」是这条契约最容易写错的地方。** 数组长度不足就是没有这个字段，
**不要写空数组占位**（`[]` 会占 2 字节，且让判空变复杂）。所以：

```
len === 3  →  只有 senses / tags / frq，没有 forms 也没有例句
len === 4  →  多一个槽。它是什么？看 typeof：
              string → forms
              array  → examples（这个词没有 forms 但有例句）
len === 5  →  forms 与 examples 都有
```

**为什么 `forms` 必须保持字符串、不能改成 `[["ran","过去式"], …]` 数组对**：
槽 3 是"挤上来"的——有 forms 的写字符串，没 forms 有例句的写数组。若 forms 也改成
数组，槽 3 会同时是"fmtrs 数组"和"例句数组"，而两者内层都是长度 2 的数组，
`typeof` 与内层长度都区分不了，运行时必然误判。**字符串 / 数组的 `typeof` 差异
是这个变长布局唯一的判别信号**，不能动。

**变位不带标签**（数据组的 `FORM_KEYS = ['p','d','i','3','s','r','t']` 只保留了形式，
丢了标签）。原稿设想 `[["ran","过去式"]]`，实现不了。见 §4.5 的渲染降级。

#### 4.2.1 `SenseGroup`

```
SenseGroup = [pos, zh[], en[]?]
```

| 位 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | `pos` | `string` | **带点**，与 ECDICT 原文一致。合法值见下。解析不到词性时为 `""` |
| 1 | `zh` | `string[]` | 中文义项，长度 ≥ 1，当前档位最多 2 条 |
| 2 | `en` | `string[]` | 英英释义，**可选**。当前档位 `enCap: 0`，全库不存在这一位 |

`pos` 的合法值（实测分布）：

```
n.(12949)  adj.(5822)  v.(5500)  ""(3661)  adv.(1265)
prep.(88)  pron.(78)   int.(74)  num.(58)  conj.(42)  aux.(14)  art.(2)
```

渲染时**去掉末尾的点**再显示（`n.` → `n`，`adj.` → `adj`），或按 §4.5 翻成中文。

**`""` 占 18%（3661 组）**：这些是从 ECDICT 解析不出词性前缀的行。
界面上显示成"无词性"或用中性样式，**不要猜成 `n.`**。

`zh` 和 `en` 是两个**独立数组、数量不对齐**，这是三者分开存的原因：
中文义项有 2 条时英文可能只有 1 条。渲染时分别铺，不要按下标配对。

#### 4.2.2 `Example`

```
Example = [en, zh]
```

| 位 | 字段 | 类型 | 取值范围 |
|---|---|---|---|
| 0 | `en` | `string` | 5–300 字符 |
| 1 | `zh` | `string` | 1–300 字符 |

**注意：例句里的中文是繁体。** 数据组的 Tatoeba 句对是繁中
（`"我長大後想當國王。"`、`"這輛車沒有以前跑得那麼順暢。"`）。这是数据现状，
实现者**不要**尝试转换（转换会引入错字且需要额外依赖）。

#### 4.2.3 词头形态

键必须全小写、无空格。实测存在少量带标点的词头（`a-road`、`a.m.`），
这些**保留**——取词算法（`word.js`）认得连字符与撇号，但点号会让 `caretAt` 取不到
完整词形，所以它们在界面上基本查不到。这是可接受的（`a.m.` 不是用户会悬停的词）。

### 4.3 变位索引（运行时建，不单独存文件）

**这个文件不再存在。** 变位信息已经在每个词条的槽 3 里，单独存一份 46,011 条的
映射表是重复存储。

实测：早先单独存过一份变位表，976 KB，其中 20,499 条是"词条映射到自己"的纯冗余，
去掉冗余后仍要 530 KB。这笔体积换给例句和英英释义，对用户价值大得多。
所以改为**运行时从 `dict.dat` 建索引**，见 §4.4。

宿主的 `index.js` 的 `ASSETS` 数组**只有两项**（`meta.json` 与 `dict.dat`），
客户端 `net.js` 的 `ASSET_PATHS` 同样只有两项。

### 4.4 运行时怎么建索引

`loadDictionary` 分两步：

```
1. GET meta.json  →  只用于展示来源/许可与诊断，缺失不致命
2. GET dict.dat   →  JSON.parse，得到 { "<词头>": Entry[] }
3. 遍历建索引
```

**建索引的顺序是契约，写反了会静默改变 50 个词的查词结果。**

```js
const lookup = new Map()

// 第一趟：所有词头先铺进去，映射到自己
for (const w in dict) lookup.set(w, w)

// 第二趟：补变位，只在键还不存在时补（变位不覆盖已有词头）
for (const w in dict) {
  const e = dict[w]
  const forms = typeof e[3] === 'string' ? e[3] : ''   // 槽3 可能是 forms，也可能是 examples
  if (forms === '') continue
  for (const f of forms.split(',')) {
    if (f && !lookup.has(f)) lookup.set(f, w)
  }
}
```

**为什么词头必须赢。** 有 221 个键"既是独立词头、又被别的词当变位"。
例：`analyses` 既是 `analyse` 的复数变位，也是一个独立词条。两种建法差 50 个键：

| 键 | 词头优先（选定） | 变位优先（错误） |
|---|---|---|
| `analyses` | → `analyses` | → `analyse` |
| `axes` | → `axes` | → `ax` |
| `bathed` | → `bathed` | → `bath` |
| `caddies` | → `caddies` | → `caddie` |
| `distilled` | → `distilled` | → `distil` |

用户悬停 `axes` 时想看的是 `axes`（斧头复数），不是 `ax`。这条与数据组
`idxFor()` 的 `if (!(f in idx))` 完全一致——**实测词头优先后，重建结果与原
变位索引（运行时从词条 forms 现场建，不再单独存文件） 逐键比对 0 处不一致**，所以这个改动是无损的。

**成本**：约 25,783 次 `Map.set`，与原先 `JSON.parse(变位索引)` 同量级
（实测建 Map 版本 31.1 ms vs 解析 0.93 MB 版本 30.7 ms）。省下 0.42 MB 传输，
解析成本基本持平。

**查询路径**（`lookup(dict, text)`）：

```
key = normalizeKey(text)          // 撇号统一 + 转小写
1. lemma = idx.get(key)           // 一步拿到原形（建索引时词头已映射到自己）
   if (lemma !== undefined) return { status:'hit', entry: dict[lemma], matchedKey: key, lemma }
2. for (cand of stemCandidates(key))   // 最多 8 个，只在未命中时跑
     l = idx.get(cand)
     if (l !== undefined) return { status:'hit', entry: dict[l], matchedKey: cand, lemma: l }
3. return { status:'miss' }
```

比原稿少一步：原稿要"先查 forms 再查词头表"，现在建索引时词头已经在 Map 里了，
一步到位。`stemCandidates` 仍是兜底（数据组的变位来自 ECDICT `exchange` 字段，
覆盖 13,793/20,499 个词条，剩下 6,706 个没有变位信息的词靠它兜）。

**性能契约**：单次 `lookup` < 0.1 ms。查询路径里不许分配、不许正则、不许切片。

### 4.5 数据现状对渲染契约的影响

这一节是给实现者的**产品降级说明**。原产品需求（"全部义项按词性分组、英英释义、
双语例句"）在当前数据档位下只能部分满足：

| 卡片分区 | 原需求 | 当前数据 | 实现者怎么办 |
|---|---|---|---|
| 义项 | 全部，按词性分组 | 每组最多 2 条中文 | 照实渲染。**不要**显示"共 N 条"之类暗示还有更多 |
| 英英释义 | 有 | **全库 0 条** | 整块**不渲染**（判空后 return null，不留空标题） |
| 例句 | 双语 | 12% 词条有，每词 1 句，中文是繁体 | 照实渲染。没有就不渲染这一块 |
| 词形变化 | 带标签（过去式/复数） | 逗号串，**无标签** | 只显示形式，不加标签。用 `ran / running / runs` 这种并列样式 |
| 考纲标签 | 四六级/考研/雅思 | 八种：`zk gk cet4 cet6 ky toefl ielts gre` | 全部支持。`config.js` 的 `tagLabel` 要覆盖八种 |

**为什么不在渲染层"补"英文释义**：那需要联网或另一份词库，违反离线约束；
也不许用中文义项机翻成英文，那是伪造数据。

**给数据组的反馈**：若后续要满足原产品需求，需要调 `corpus` 档位
（`enCap: 1` 且 `enFrqMax` 放宽、`exMax: 2~3`）。体积会涨，届时可能触发
§3.4 的二进制格式例外条款。这是产品决策，不在本次范围。

## 5. 交互状态机

### 5.1 状态

```
idle        没有悬停在任何可查的英文词上
pending     停在候选词上，正在等 hoverDelayMs
popover     小浮层可见
card        大卡片可见
suppressed  主动压住（滚动中 / 流式中 / 禁用 / 刚按过 Esc）
```

`pending` 与 `popover` 分开是必要的：合成一个状态就无法表达「已命中但还在犹豫」，
而这段犹豫期正是判定「用户是扫过去还是停下来」的唯一窗口。

### 5.2 迁移表

| 从 | 事件 | 到 | 动作 |
|---|---|---|---|
| `idle` | 指针进入合格目标 | `pending` | 记下候选锚点、起点坐标、起算时刻 |
| `pending` | 指针移动超出 `stableRadiusPx` | `pending` | 重置计时与起点坐标 |
| `pending` | 停稳 ≥ `hoverDelayMs` 且复核通过 | `popover` | 量矩形、查词、摆浮层 |
| `pending` | 离开 / 目标不再合格 | `idle` | 清候选 |
| `popover` | 移到**另一个**词 | `pending` | 清当前浮层候选，重新计时 |
| `popover` | 移出锚点与浮层外扩区 ≥ `leaveGraceMs` | `idle` | 收起 |
| `popover` | 指针进入浮层本体 | `popover` | 取消收起计时，改用 `popinGraceMs` |
| `popover` | 点击（`pickUpgradeTarget` 返回 `open`） | `card` | 摊开词条、量卡片、摆位 |
| `card` | 点同一个词 | `idle` | 收起（切换语义） |
| `card` | `Esc` | `idle` | 收起 |
| `card` | 移出卡片 ≥ `cardLeaveGraceMs` 且未固定 | `idle` | 收起 |
| 任意 | 开始滚动 | `suppressed` | 收起浮层，记下时刻 |
| 任意 | 流式输出开始 | `suppressed` | 收起浮层 |
| `suppressed` | 滚动停止 ≥ `scrollDismissMs` | `idle` | 恢复 |
| `suppressed` | 流式停止 ≥ `streamSettleMs` | `idle` | 恢复 |
| `suppressed` | 窗口失焦 | `suppressed` | 保持压住 |

非法迁移（例如 `idle` → `card`）一律**静默丢弃**，不抛错、不打日志 ——
事件来自浏览器，时序交错是常态。

### 5.3 时间参数（全部给死数）

| 参数 | 默认值 | 范围 | 为什么是这个数 |
|---|---|---|---|
| `hoverDelayMs` | **120 ms** | 40–2000 | 低于 80 ms 时快速横扫会逐个触发；高于 200 ms 会让人觉得「卡住了」。120 ms 大约是「停下手指」的自然停顿 |
| `stableRadiusPx` | **3 px** | 0–24 | 鼠标在静止时会因手抖产生 1–2 px 抖动。3 px 容差能吃掉抖动又不至于把「真的在移」判成静止 |
| `leaveGraceMs` | **180 ms** | 0–2000 | 鼠标从词移到浮层要跨过一段空白。180 ms 足够走完 20–40 px，短到不会让浮层「赖着不走」 |
| `popinGraceMs` | **420 ms** | 0–4000 | 已经在浮层里时给更宽的时间：用户可能在里面挑文字复制 |
| `upgradeDelayMs` | **0 ms** | 0–1000 | 点击升级是明确的意图，不需要防抖。留这个参数是为了将来加「双击才开卡片」的档位 |
| `cardLeaveGraceMs` | **220 ms** | 0–2000 | 卡片大，鼠标划出去又回来的概率更高，比浮层宽一点 |
| `scrollDismissMs` | **260 ms** | 0–2000 | 略大于一次惯性滚动的停顿间隔，避免滚动尾巴上误弹 |
| `streamSettleMs` | **400 ms** | 0–5000 | 流式输出每个 chunk 间隔可能到 200–300 ms。400 ms 能覆盖 chunk 间隙而不让人觉得「生成时查不了词」 |
| `repositionThrottleMs` | **80 ms** | 16–500 | 滚动时重算位置需要节流，80 ms 约等于每 5 帧一次。低于 16 ms 无意义（不到一帧） |
| `maxHoverPerMinute` | **60** | 1–600 | 病态触发的熔断。正常阅读远达不到 60 次/分；超限进 suppressed 60 s 并指数退避 |

### 5.4 三个容易写错的判定

**一、`pending` 到期时要复核，不能只看定时器。**

鼠标扫过一行时 `pointermove` 的频率是 60–120 Hz，远高于 120 ms。如果只是
「移动就重置定时器」，那么在一行字上快速扫过时，最后一次移动之后仍有 120 ms 静默，
浮层就会**在用户已经离开的位置**弹出来。

正确做法是到期时复核三件事：指针当前坐标与起点距离 ≤ `stableRadiusPx`、
`caretAt` 仍然落在同一个词上、目标元素仍在文档里。三条全过才进 `popover`。

**二、鼠标从词移到浮层，中间必然经过别的词。**

浮层在词下方 6 px，鼠标移过去时可能先掠过下一行的词。如果「离开锚点就立即收起」，
浮层会在这段路途中消失，用户永远够不到。

正确做法是 `leaveGraceMs` 的**时间**判定与「是否在锚点或浮层外扩矩形内」的
**空间**判定联合：只要还在外扩矩形内（`pad` 取 8 px），就不启动收起计时。

**三、流式输出会持续滚动。**

生成回答时宿主会不断把视图往下带（`scrollTop` 单向增加）。如果把这当成用户滚动，
浮层会在生成过程中反复消失。判据见 `hit.js` 的 `isProgrammaticScroll`：
单向、连续、且最近 `streamSettleMs` 内没有 `pointerdown` 记录，就按程序滚动处理，
不触发 suppressed，只在新位置重算锚点。

## 6. Host 侧与 Client 侧的职责切分

| 能力 | 宿主侧 | 客户端 | 为什么 |
|---|---|---|---|
| 词库文件读取 | ✅ | — | 客户端拿不到文件系统 |
| gzip / ETag / 304 | ✅ | — | 属于 HTTP 层 |
| 路径白名单 | ✅ | — | 安全边界，只在服务端有意义 |
| 词库解析 | — | ✅ | 放宿主侧等于每次查询跨进程 |
| 建索引 | — | ✅ | 同上 |
| 查词 | — | ✅ | 必须 0.05 µs 级 |
| 取词算法 | — | ✅ | 依赖 DOM |
| 坐标反查 / 量矩形 | — | ✅ | 依赖 DOM |
| 渲染浮层与卡片 | — | ✅ | 依赖 React |
| 交互状态机 | — | ✅ | 高频，不能跨进程 |

判据一句话：**碰文件系统的在宿主，碰 DOM 的在客户端，只有词库文本跨过一次边界。**

宿主侧代码量约 200 行（全部 TODO 空壳），客户端约 1500 行。这个比例是合理的：
这个插件本质上是一个前端功能，宿主侧只是它的静态资源服务器。

### 6.1 为什么不在宿主侧提供一个「查词工具」

考虑过：注册一个 `hover_dict_lookup` 工具让模型自己查词。否决理由：

1. 模型查词和用户查词是两个需求。用户悬停需要 0.05 µs，模型查词可以走工具调用，
   但那个需求不存在（模型不需要查中文释义）；
2. 工具是面向模型的注册面，用户看不到。加了它反而要在设置里解释「这个工具是干什么的」；
3. 每个工具都有 schema 与描述的开销，会进每次请求的 system prompt。

如果将来真的需要（比如用户想让模型在回答里主动标注生词），那是一个**独立插件**，
不要塞进这个。

## 8. 已知风险与缓解

### 风险一：DOM 选择器随宿主版本变化

**症状**：宿主升级后插件完全不工作，或者开始在用户消息里弹词。

**为什么会有这个风险**：`[data-chat-flow-kind="assistant-step"]` 这类属性是宿主的
内部实现细节，不是公开 API。上游没有承诺它永久存在。

**缓解**：

1. 所有选择器集中在 `hit.js` 的 `SELECTORS` 一个对象里，升级后只改一处。
2. 判定**优先用语义标签**（`pre` / `code` / `a[href]` / `input`），不依赖类名。
   宿主的类名带构建哈希（如 `AkCqbG_`、`ZITbJG_`），每次构建都变；标签不会。
3. 加一条**启动自检**：`apply` 时如果 `document.querySelector(SELECTORS.allowedRoot)`
   找不到，`console.warn` 一行说明「当前宿主版本可能改了选择器」。
   不要静默失败——静默失败用户只会以为插件坏了。
4. 在 README 的「兼容性」一节写明：本插件针对的宿主 DOM 契约是什么，
   以及怎么自己改。

**兜底**：即使 `allowedRoot` 找不到，插件也只是不弹词，不会影响宿主任何功能。
这是「宁可失效，不可做错」的设计。

### 风险二：流式输出时误触发

**症状**：回答正在生成时，浮层在屏幕上闪来闪去，或者追着一个已经变了的词。

**根因有三层**，分别对应三个机制：

1. **正文在变**：每次 chunk 到达，宿主重渲染 markdown，我们的锚点可能指向
   已脱离文档的文本节点。→ `anchor.js` 的 `isAnchorStale` 每次重算前判
   `isConnected` 与矩形位移，失效就收起。
2. **视图在滚**：宿主把视图往下带。→ `hit.js` 的 `isProgrammaticScroll`
   区分程序滚动与用户滚动，程序滚动不进 suppressed，只重算位置。
3. **用户可能正想查词**：生成中看到生词是正常需求。→ 不强硬禁止，
   但 chunk 到达后的 `streamSettleMs`（400 ms）内不**新**弹浮层；
   已经在显示的浮层保持不动（它的锚点会随正文移动而重算）。

**最坏情况**：流式输出极快时浮层跟随抖动。缓解手段是把重算节流到
`repositionThrottleMs`（80 ms），并在同一次 chunk 批次的多次重排里只取最后一次。

### 风险三：词库缺词

**症状**：用户悬停在 `Kubernetes` 上，什么都不出现，用户以为插件坏了。

**分层处理**：

| 情况 | 界面行为 | 理由 |
|---|---|---|
| `status: 'miss'`（词库没收录） | **不弹** | 查不到的常见词是专有名词、代码标识符、人名。给每个都弹「未收录」比不弹吵得多 |
| `status: 'not-ready'`（还在加载） | 停留超过 800 ms 时显示一行「词库加载中…」 | 只在用户真的在等的时候出现，扫过去不会看到 |
| `status: 'error'` | 一行「词库未就绪，点此重试」，可点 | 这是**真的坏了**，必须让用户知道并且能修 |
| `E_DISABLED`（插件被关掉） | 静默，不弹任何东西 | 用户主动关的，不要再吵他 |

**为什么 miss 要静默**：一屏英文回答里，变量名、函数名、缩写的比例可能到 20%。
如果每个都弹一次「未收录」，这个插件会变得没法用。

**数据层面的缓解**：见 §11 与 `docs/数据契约给数据组.md` —— 覆盖率约一半是
已知且接受的（核心 2 万词覆盖日常阅读的绝大多数；剩下的本来也不该查）。

### 风险四：浮层挡住正文导致读不下去

**症状**：浮层正好盖住下一行，用户想看下一行就必须移开鼠标。

**缓解**：`position.js` 的翻面规则（下方放不下就翻到上方），加上贴边夹取。
大卡片的高度上限是视口的 0.7 倍，超过就内部滚动。

**已知不足**：在很窄的窗口里（< 480 px），卡片和浮层都可能盖住大半视野。
这种情况下 `computeCardPlacement` 会退回「下方」摆放，且卡片宽度受
`cardMaxWidthPx` 与视口宽度双重约束。如果实测仍然难受，下一步的方向是
「窄窗口改用底部抽屉」——这是产品决策，留给后续。

### 风险五：与宿主或其他插件的冲突

**已知的冲突面**：

1. **抢点击**：我们只听 `shell.overlay` 上的点击，不 `preventDefault` 正文的点击。
   升级判定里有一条「按了修饰键就不升级」，留给用户自己的快捷键。
2. **抢右键菜单**：完全不监听 `contextmenu`。
3. **抢滚动**：只读 `scrollTop`，不调 `scrollTo`。
4. **其他插件的覆盖层**：`shell.overlay` 是 list 类型的 slot，多个插件共存。
   我们用独立的 `id`（`hover-dict.popover` / `hover-dict.card`），不占用 keyed 位置。
   注意我们的根节点是 `pointer-events: none`，只有本体 opt-in，
   否则会挡住别的插件的浮层。

### 风险六：性能在低端设备上不可接受

**实测数据**（本机，见 §3.3）：加载 12–16 ms。外推低端设备 60–140 ms。

**缓解**：

1. 加载时机是首帧之后的 `requestIdleCallback`，不阻塞首屏；
2. 加载期间查询返回 `not-ready`，界面显示「加载中」而不是空白；
3. 悬停路径本身是内存直查（0.05 µs），与设备性能基本无关；
4. 如果将来词库扩到 3 MB 以上，按 §3.4 的例外条款换二进制格式。

## 9. 构建方式

客户端产物 `client.js` 是**单文件**，形状固定：

```js
window.__ModuleLoader__.load({
  id: 'dsh-hover-dict',
  factory: (require) => { /* … */ return module.exports },
})
```

### 9.1 为什么必须是这个形状

宿主不给你 `import`。client-modules 把每个浏览器半当作**经典脚本**用 `<script>`
加载（已核实：loader 侧是 `document.head.append(<script>)`），脚本执行时只做一件事：
调 `window.__ModuleLoader__.load(...)` 把自己登记进模块表。宿主随后调用 `factory`，
把 `require` 传进来——能拿到的只有宿主已登记的静态模块（`react` 等）。

写成 ES module 会直接 `SyntaxError`，整个 slot 白掉，而且宿主那边没有显眼报错
（loader 只会记一条 `loaded without registering "<id>" via __ModuleLoader__.load`）。

同理不能有顶层 `await`、不能用 `import.meta`、不能用 `export`。

### 9.2 为什么源码分模块 + build.mjs 拼接

照抄 `dsh-Reading` 的做法，理由三条：

1. **零构建链**。为十来个纯 ES 模块引入 esbuild / rollup，会让「clone 下来就能装」
   变成「先装一条构建链」。本包的 `dependencies` 是空的，这个性质值得保住。
2. **源码能被 node 直接 import 测**。`word.js` / `position.js` / `dict.js` 里的纯函数
   可以用 `node --test` 直接跑，不需要先打包。
3. **产物可 review**。单文件产物在 diff 里能看，打包器的产物不能。

`build.mjs` 要做的事（与 dsh-Reading 同构）：

```
按 MODULES 固定顺序读 client/src/*.js
  → 每个包进自己的 IIFE（防同名遮蔽）
  → 剥掉 import/export（按行扫描状态机，不用裸正则）
  → 加构建期前导（React、h、useState… 由宿主 require 提供）
  → 拼进 __ModuleLoader__ 外壳
  → 写 client.js
--check 模式只校验磁盘上的 client.js 与源码同步
```

**模块顺序写死在 `MODULES` 数组里，不用 readdir**：目录遍历顺序不保证，
顺序一变 `--check` 就会随机变红；而且模块之间有下行依赖。

前导里注入的名字（**源码里不要重复声明**）：`React`、`h`、`useState`、`useEffect`、
`useLayoutEffect`、`useRef`、`useMemo`、`useCallback`。

### 9.3 样式怎么进

宿主认的做法（已核实 client-modules 的 `claimStyles`）：

- 在 `factory` 执行期间插一个 `<style>` 到 `document.head`；
- 带 `data-plugin-css="<稳定 id>"`，宿主据此记账；
- **不要**用 `data-plugin` 手动标记（那是 loader 自己给未标记 style 打的）；
- 幂等：同 id 已存在就不重复插，内容变了才替换 `textContent`。

`overlay.js` 的 `ensureStyle(doc)` 负责这件事。

颜色一律用 `--dsw-alias-*` 语义 token（实测存在的有：`label-primary`、
`label-secondary`、`label-tertiary`、`bg-layer-1`、`bg-layer-2`、`bg-base`、
`border-l1`～`border-l4`、`brand-primary`、`link`、`interactive-bg-hover`、
`markdown-inline-code` 等），**不要写死颜色、不要自己判断暗色主题**。
圆角用 `--dsw-radius-sm/md/lg`，浮层阴影用 `--dsw-elevation-panel`
（elevated surface 用 `box-shadow`，**不要**再叠 `border` —— 主题的 elevation
规范不接受两者并存）。

## 11. cordis.patch.yml 完整内容

```yaml
- insert:
    - id: hover-dict
      name: 'dsh-hover-dict'
```

只有一行，且**不写 config**。

- `id: hover-dict`：Loader 的行标识。短、便于用户在 profile 里
  `- id: hover-dict` 覆盖 config；不与包名重复，避免 `- id: dsh-hover-dict, name: 'dsh-hover-dict'` 这种冗余。
- `name: 'dsh-hover-dict'`：必须是包名，与 `package.json` 的 `name` 逐字一致。
- 不写 config：所有键都有默认值（见 §7.1）。在这里固定会让用户覆盖时
  要连这里一起改，而且上游删行后 override 会**静默失效**。

**没有 client 相关条目**：`package.json` 的 `dsh.client` 声明之后，client-modules
会自己扫描到本包并把 `exports["./client"]` 作为一条 row 挂进 `__DSH_BOOT__`。
多写一行反而会重复注册。

## 12. 实现顺序建议

给实现者的施工顺序。每一步都能独立验证，不要跳。

|---|---|---|
| 1 | `word.js` 全部函数 + 单测 | `wordAt` 的 8 个边界用例全过 |
| 2 | `position.js` 摆位 + 单测 | 四个角落 + 窄视口用例全过 |
| 3 | `index.js` 路由 + 手写一个假 data/ | `curl` 三个文件都能下到，304 生效 |
| 4 | `net.js` + `dict.js` 加载与查询 | node 里用假词库跑通 `lookup` 的 4 条分支 |
| 5 | `hit.js` 判定 | 用 jsdom 造一段含 code/link/公式的 HTML，断言各种 target |
| 6 | `anchor.js` 量矩形 | 真实浏览器里对一段已知文本断言 rect 数量 |
| 7 | `overlay.js` 高亮 + 浮层 | 手动悬停，浮层出现在词下方 |
| 8 | `card.js` 大卡片 | 点击升级、Esc 收起、固定开关 |

第 3 步之前不要接真数据——数据组的产出还没定稿，先用假的把管道跑通。

## 13. 数据来源与合规

| 数据 | 来源 | 用途 | 许可 |
|---|---|---|---|
| 释义、词性、考纲标签、柯林斯星级、牛津 3000 | ECDICT | 主词条 | MIT |
| 英中双语例句 | Tatoeba（英中句对 78,293 组，筛后约 6.9 万） | 例句 | CC-BY-2.0-FR |

要求：

1. `meta.json` 的 `licenses` 字段必须如实填写；
2. 界面里要能看到来源与许可（大卡片底部一行小字，或 README 的「数据来源」一节）；
3. ECDICT 的 `pos` 字段全空，词性是从 `translation` 每行的 `n.` / `v.` / `a.` / `ad.`
   前缀解析出来的（87.7% 的行有前缀，剩下的没有词性，构建期要丢掉或归到 `n`——
   口径见 `docs/数据契约给数据组.md`）；
4. ECDICT 的 `detail` 字段是空的设计占位，**没有例句**，例句全部来自 Tatoeba。
